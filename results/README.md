## 汇总表约定

一行一次测量（一个配置 + 一个场景 + 一次运行），**不合并、不预先平均**：

| 列 | 含义 |
|---|---|
| `exp_id` | 实验编号，对应 `docs/02_过程记录/实验记录/EXP-....md` |
| `date` | 测量日期 |
| `milestone` | M1–M6 |
| `config` | 配置标识（如 `vision_only` / `grade_only` / `full` / `extrap_on` / `extrap_off`） |
| `metric` | 指标名（用统一叫法，见术语表） |
| `value` | 数值 |
| `unit` | 单位（ms / % / fps / KiB / cm / ℃） |
| `n` | 样本数 |
| `note` | 异常、剔除、环境异常等说明 |

**为什么一行一次测量**：预先平均会丢掉方差。而"这个指标稳不稳"往往比"这个指标多好"更重要。

## 失败台账（`失败台账.csv`）—— 和汇总表分工不同

| | 指标表 | 失败台账 |
|---|---|---|
| 粒度 | 一次测量 | **一次判错** |
| 回答 | 这个数是多少 | **这个数是怎么错的** |
| 谁填 | 跑完实验汇总 | **当场填，或从日志里挑出来填** |
| 规模 | 几十行 | 几十到几百行，越多越好 |

**只有判错的帧进这张表。** 判对的不进——判对的数量由指标表的 `n` 反映。

**为什么值得单独建一张表**：

1. 论文里最有价值的一节是 Failure Analysis，不是 Method。审稿人和面试官真正想知道的是"它在哪种情况下会坏"，这一节的全部素材来自这张表。
2. 面试被问「你遇到最大的困难是什么」，答得出具体场景、具体数值、具体处置的人，和只能讲流程的人，是两个层次。
3. 这是整个项目里**唯一无法被 AI 生成、也无法被同学抄走**的数据 —— 它只能来自你真的跑过、真的错过。

### 填表纪律

- **判错就填，不筛。** 挑着填等于造假，而且挑完的分布没法用。
- `归因` 一栏必须写**机制**，不能写现象。写「光照不足导致概率整体压平」，不写「环境不好」。
- `处置` 一栏写**改了什么**。没改就写「暂不处理」，别空着——空着三个月后自己都不记得为什么放过了。
- `视频文件` 对应 10 秒片段，命名与帧号对齐。答辩时按帧号点名调出来放。
- 表里出现新的失败类型时，回来更新 `docs/06_风险与变更/01_风险登记册.md`。

## 什么时候该出图

| 图 | 什么时候 | 说明 |
|---|---|---|
| 风险—覆盖率曲线 | M2 起 | 横轴覆盖率、纵轴错误率；标出目标点（触发率 30%） |
| 触发率—召回 散点 | M4 | 说明阈值选择的合理性 |
| A/B 分布图（补位开/关） | M5 | 两个箱线图 + 中位数标注 |
| 功耗—温升—帧率包线 | M5 | 三轴同时看，横轴时间 |
| 时延分解条形图 | M3 | 按阶段拆（抓帧/预处理/推理/后处理/串口） |

图放 `figures/`，**PNG 入库**（单张 < 500 KB），生成脚本放 `tools/eval/`。**图必须能重画**——手调的图三个月后没法更新。

## 三条纪律

1. **不挑数据。** 跑了 20 次，20 次都进表，哪怕有 3 次明显异常——异常在 `note` 里说明，不是删掉。
2. **不改口径。** 测完发现"不好看"就想改定义，等于造假。要改就走 [变更记录](../docs/06_风险与变更/02_变更记录.md)，且**旧数据作废重测**。
3. **每个数有日志。** 表里的一行 ↔ `raw/` 里的一份日志 ↔ 一份实验记录。**断掉任何一环，这个数就不能写进报告。**
