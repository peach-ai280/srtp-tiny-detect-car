## 一、一句话

> 别人在证明"MCU 能跑目标检测"，我们处理的是另一半问题：**它跑得慢、跑得不准的时候，车该怎么办。**

项目名里的"轻量化目标检测"是已经被人做透的事——2018 年 CMSIS-NN 打通了这条路，ST 官方 model zoo 连实测数据都放出来了。所以我们不从"能不能跑"切进去，从**"跑的结果不可信时怎么办"**切进去：

1. **让模型自己说这一帧靠不靠得住**——用四个来自推理过程的信号（间隔、量化饱和率、帧间一致性、输出熵），给出 可用 / 存疑 / 弃用 三档判定；
2. **什么时候去问超声波，由模型决定**——把传感器融合里的"权重"换成"时机"，超声平时休眠，只在存疑时被唤醒来做定向复核；
3. **两帧之间怎么补上**——4 fps 的检测框 + 100 Hz 的陀螺与编码器，把旧框推演到当前时刻，交给控制环。

第 3 条我们自己在文档里标成**工程创新，不是方法创新**。高频惯性补低频视觉是控制领域的成熟常识，它的价值在于"在几十 KB RAM、没有浮点余量的定点环境里做到能用，并把收益量化出来"。

## 二、为什么值得做：一个数

三个互相独立的来源，给出同一个量级——在 STM32H7 上跑 192×192 的检测网络，端到端要两百多毫秒：

| 来源 | 平台 | 数字 | 口径 |
|---|---|---|---|
| ST 官方基准 | STM32H735 @550 MHz | **105.8 ms** | SSD-MobileNetV1-0.25 192×192 INT8，纯推理 |
| 开源复现 [1] | STM32H743 + OV5640 | **240 ms** | 端到端含采集与后处理，mAP 31.8%，约 4–5 FPS |
| 学术基准 [2] | STM32H7A3 @192 MHz | **359 ms** | TinyissimoYOLO 最小检测网络，单帧 |

于是有了一行算术，也是整个项目的起点：

```
0.3 m/s × 240 ms = 7.2 cm
```

车以 0.3 m/s 行进时，一帧检测的时间里车身已经前移 7.2 cm——比一个物料盒（约 5 cm）还宽。**感知更新率 4 Hz，控制环 100 Hz，中间那 23 个控制周期拿到的都是旧位置。** 这不是假设出来的场景，是任何一台把检测塞进 MCU 的小车都会遇到的事。

现有工作大多停在前半段：给出一个"不确定度分数"，然后结束。**没人回答这个分数该触发什么物理动作。** 这一格是空的，我们进去。

## 五、怎么跑起来

**当前还不能跑。** 仓库处于立项期，`firmware/`、`tools/` 里只有目录约定和接口说明，没有可执行代码。第一条能跑通的命令预计出现在里程碑 1（2026-11-30）之后：Cube.AI 生成的官方模型在 H743 板上出第一帧推理耗时。

到那时这里会替换成：

```bash
# 1) 拉代码
git clone <repo-url> && cd srtp-tiny-detect-car

# 2) PC 端：量化 + 精度标定（需要 Python 3.10+ 与 TensorFlow）
python -m venv .venv && . .venv/bin/activate
pip install -r tools/requirements.txt
python tools/quantize/quantize_int8.py --config tools/quantize/configs/yolo_lc_192.yaml

# 3) 板端：生成 Cube.AI 工程并编译固件（需要 STM32CubeIDE 与 X-CUBE-AI 扩展包）
#    生成的 C 工程不直接入库，产物说明见 models/README.md
```

在此之前，请先读文档。**我们不先把代码写出来再补文档，也不先用文档假装有代码。**
