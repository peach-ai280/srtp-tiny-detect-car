## 一、C 代码（固件）

### 1.1 命名

| 对象 | 风格 | 例子 |
|---|---|---|
| 函数 | `模块_动作`，小写下划线 | `sonar_trigger_once()` |
| 文件内静态函数 | 前缀 `s_` 或加模块名 | `static void s_reset_state(void)` |
| 变量 | 小写下划线 | `frame_cnt`, `sat_ratio_q8` |
| 全局变量 | **加模块前缀**，且尽量不用 | `g_percept_state` |
| 宏 / 常量 | 全大写下划线 | `JUDGE_TH_S2_HIGH` |
| 类型 | `_t` 结尾 | `judge_grade_t` |
| 定点量 | **必须在名字里带格式** | `pos_x_q8_8`, `v_mm_s` |

**定点量的命名是硬要求。** `pos_x` 这种名字在定点项目里是灾难源头——没人知道它是 mm 还是 m，是浮点还是 Q8.8。**名字里写清单位和格式，比注释管用。**

### 1.2 必须遵守的六条

1. **中断里只做搬运。** 计算放到任务/主循环里。中断里 `printf`、`malloc`、长循环一律禁止。
2. **不动态分配。** 不用 `malloc/free`。全部静态或全局数组。理由：堆碎片在跑 30 分钟的车上会变成"随机死机"，而这类 bug 极难复现。
3. **头文件只放声明。** 不在 `.h` 里定义变量（`extern` 声明可以）。
4. **魔数必须命名。** 出现两次以上的字面量就该有名字。
5. **`volatile` 只用于真并发的量**（中断与主循环共享的标志、外设寄存器）。滥用的后果是编译器优化被无谓关掉，代码变慢还查不出原因。
6. **错误要能被看到。** 每个可能失败的调用（HAL 返回 `HAL_xxx`）都要判断，失败时置错误码并（可开关地）打日志。**不能 `(void)HAL_xxx()` 了事。**

### 1.3 注释

写"为什么"，不写"是什么"。

```c
/* 差 */
// 判断 s2 是否大于阈值
if (s2 > JUDGE_TH_S2_HIGH) { ... }

/* 好 */
/* 饱和率过高说明量化已经失真，这一帧的框不可信 —— 不看分数，直接弃用。
 * 阈值取验证集错误帧分布的第 70 百分位，见 docs/03_技术方案/03_帧级可信度判定.md */
if (s2 > JUDGE_TH_S2_HIGH) { ... }
```

**函数头注释至少写清三件事**：输入的单位与格式、输出、在什么条件下会被调用。

### 1.4 格式

- 4 空格缩进，不用 Tab（编辑器配 `.editorconfig` 已处理）
- 行宽 ≤ 100
- `if/for/while` 必须带花括号，哪怕只有一行
- 文件末尾留一个空行

有 `.clang-format` 的工程按它跑一遍再提交。**格式问题不要出现在 review 里浪费时间**——用工具解决。

## 二、Python（工具链）

- Python ≥ 3.10，**必须用虚拟环境**（`.venv` 已在 `.gitignore` 里）
- 依赖写进 `tools/requirements.txt`，**带版本号**（`numpy==1.26.4` 而不是 `numpy`）
- 脚本**必须能用命令行参数跑**，不许把路径写死在代码里：

```python
# 差：别人拿到跑不了
data = open("D:/我的文件/数据集/labels.txt")

# 好
ap = argparse.ArgumentParser()
ap.add_argument("--labels", required=True, type=Path)
args = ap.parse_args()
```

- 处理数据集的脚本要**打印进度和统计**（处理了多少、跳过了多少、为什么跳过）
- 随机性要固定种子（`--seed`），否则别人复现不出你的数

```
firmware/
  perception/          # H743 感知板

  chassis/             # F103 底盘板
    ...
tools/
  quantize/            # 量化脚本 + configs/
  eval/                # 评估脚本（算 S1–S4、画风险—覆盖率曲线）

```

**CubeMX 生成的代码与手写代码分开目录。** 重新生成工程时，生成目录整体覆盖，手写目录不受影响——**这一条能省掉无数次"重新生成把代码冲掉了"的崩溃。**

## 四、绝对不提交的东西

| 不提交 | 原因 |
|---|---|
| 编译产物（`build/`, `*.o`, `*.elf`, `*.bin`, `*.hex`） | 无意义，且会冲突 |
| Cube.AI 生成的中间模型文件（`*.bin` 权重大文件） | 体积；用 Release 或列出生成命令 |
| IDE 配置（`.vscode/` 里的个人设置、`.ioc` 以外的本地配置） | 各人不同。`.ioc` 要提交 |
| 数据集、日志、截图原图 | 体积，见 [数据管理规范](05_数据管理规范.md) |
| 任何密钥、token、WiFi 密码 | 安全 |

`.gitignore` 已经把这些排掉。**提交前看一眼 `git status`，别 `git add -A` 就走。**

## 五、代码评审看什么

别人的 PR 进来，按顺序看这四条，不用逐行抠：

1. **能不能看懂它想干什么**（看不懂就是注释或命名的问题）
2. **失败路径有没有处理**（返回码、超时、边界值）
3. **有没有踩上面 1.2 的六条**（尤其是中断里干活、动态分配）
4. **数字从哪来的**（阈值、系数有没有出处）

风格问题不评论——交给格式化工具。**评审只讨论"对不对"和"为什么"。**
