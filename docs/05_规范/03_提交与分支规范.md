# 提交与分支规范

> 提交历史是这个项目**最不会说谎的一份记录**。三个月后回看，"我们到底做了什么"能直接从 `git log` 读出来——前提是每次提交都写清楚。
>
> **状态：试行。** 仓库从 2026-10-26 起就在按这个写提交信息，规则本身可能还会改——改的依据是实际写起来别扭的地方。

---

## 一、提交信息

格式：`类型(范围): 做了什么`

```
feat(judge): 实现 S1 分数间隔与 S2 输出层饱和率
fix(comm): 修正串口包长度校验，之前少算 2 字节 CRC
docs(adr): 记录双板架构决策
exp(m2): 补充 INT8 量化在 160x160 输入下的精度损失
refactor(postproc): 把 NMS 从浮点改成定点，逻辑不变
test(chassis): 加一个 pid 阶跃响应的离线测试
chore(deps): 升级 numpy 到 1.26.4
```

| 类型 | 用在哪 |
|---|---|
| `feat` | 新功能（能跑的代码） |
| `fix` | 修 bug |
| `docs` | 文档（本仓库大部分提交会是这个） |
| `exp` | 实验相关（脚本、配置、结果） |
| `refactor` | 不改行为的重写 |
| `test` | 测试 |
| `chore` | 依赖、配置、杂事 |

**范围**（括号里）：`judge` / `comm` / `postproc` / `sonar` / `chassis` / `quant` / `eval` / `docs` / `adr`。

**三条要求**：

1. **说做了什么，不说"更新""修改"**。"update file" 这种提交在一年后毫无价值。
2. **一次提交做一件事。** 改 bug 顺手格式化全文件，会让 review 找不到重点。
3. **AI 参与起草的代码，在正文里加一行** `[ai-assisted]`，说明哪部分、你怎么核对的（见 [AI 使用规范](01_AI使用规范.md)）。

## 二、分支

| 分支 | 用途 | 存活时间 |
|---|---|---|
| `main` | 随时可编译、可演示 | 永久 |
| `feat/<简短描述>` | 一个功能 | 合并后删 |
| `fix/<简短描述>` | 一个修复 | 合并后删 |
| `exp/<编号或主题>` | 实验（可以不合并，留着备查） | 长期可留 |
| `docs/<主题>` | 文档较大改动 | 合并后删 |

```
feat/judge-s2-saturation
fix/uart-crc-length
exp/m2-quant-160
docs/milestone-m1-review
```

**`main` 必须可编译。** 这是唯一的硬规则——如果 `main` 编译不过，别人拉下来第一件事就是修你的烂摊子。

## 三、流程

```bash
# 1. 从最新 main 开分支
git switch main && git pull
git switch -c feat/judge-s2-saturation

# 2. 小步提交（一天至少一次）
git add firmware/perception/App/Src/judge.c
git commit -m "feat(judge): 实现 S2 输出层饱和率统计"

# 3. 推上去，开 PR
git push -u origin feat/judge-s2-saturation
```

**PR 里写三件事**（模板已备好）：

1. 这个 PR 做了什么（一两句）
2. **怎么验证的**（跑了什么、看到什么现象、哪个实验编号）
3. 有什么没做 / 有什么已知问题

第 2 条是重点。**"代码写完了"不是验证，"板子上跑出 3.2 fps，日志在 EXP-20270410-01" 才是。**

## 四、合并

- **至少 1 人看过**（不含作者）。文档类改动可以只看"通不通顺"；代码类要看 [代码规范](02_代码规范.md) 第五节那四条。
- 用 **squash merge**，一个有意义的提交比十个 "wip" 干净。
- 合并后删分支。
- `main` 上**不做实验性提交**。想快速试，就在自己分支上试，别推 `main`。

**一个人做的小改动**（改错别字、补一行说明）可以直接推 `main`，不必开 PR。**规则存在的目的是防止事故，不是制造流程。**

## 五、里程碑打 tag

每个里程碑验收通过，打一个 tag，内容对应那一级的产出：

```bash
git tag -a m1-selection -m "M1 调研与选型验收：相机出图、官方模型上板、内存账对齐"
git push origin m1-selection
```

tag 名：`m1-selection`、`m2-quant`、`m3-onboard`、`m4-fusion`、`m5-optimize`、`m6-final`。

**tag 是给评审和后来的自己看的**：`git diff m1-selection m3-onboard` 就能看到"从选型到上板，代码到底变了什么"。这比任何进度报告都真实。

## 六、几条经验（踩过才知道）

1. **每天至少提交一次。** 攒一周再提交，等于把一周的工作放在一个篮子里——硬盘坏一次就没了。
2. **改之前先 commit。** 要重构一个能跑的模块，先在干净状态提交一次，改坏了能回去。
3. **大文件永远不进 git。** 一旦进了历史，删掉也还在（要 rewrite history，很麻烦）。`.gitignore` 先配好。
4. **不确定要不要提交的，先提交到分支。** 分支不花钱，丢失的工作花时间。
5. **`git log --oneline` 要能当工作日志读。** 如果读不出来，说明提交信息写废了——而这份日志恰好是结题报告"工作过程"一节最好的素材。
