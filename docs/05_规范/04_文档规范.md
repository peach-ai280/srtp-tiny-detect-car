# 文档规范

> 文档的目标只有一个：**让没参与的人照着能做出来。** 做不到这一点的文档，长度都是成本。

---

## 一、每份文档开头要有一个状态块

```markdown
> 状态：设计稿 v0.1（2026-10-26）　｜　负责人：陶家宇
> 本文中的数值除标注"已测"外均为设计值或估算，实测后回填。
```

三件事必须写：**是什么状态（设计稿/已定稿/已实测）、什么日期、谁负责**。

**"设计稿"与"已定稿"要分清楚。** 把估算写成结论，是这个仓库最不能犯的错——它会让三个月后的你相信一个没验证过的数。

---

## 二、写作的六条

1. **结论前置。** 每节第一句说结论，后面才是理由。评审只看第一段就能判断要不要细读。
2. **数字进表格。** 段落里不超过两个数字，超过就做表。表格有单位列。
3. **一处一个真相。** 指标定义只写在 [指标定义与验收口径](../03_技术方案/06_指标定义与验收口径.md)，别处一律引用，不复制。复制的东西一定会不同步。
4. **中英混排加空格**（"使用 STM32H743 核心板"），全角标点，专有名词保留原文（Cube.AI、DCMI、INT8）。
5. **相对链接**，`../03_技术方案/01_系统架构.md` 这种，**不用绝对路径、不用 `D:\`**。链接必须能点开——PR 前自己点一遍。
6. **图优先用 mermaid**（GitHub 直接渲染），不用截图。截图里的文字搜不到，也没法改。

---

## 三、结构约定

```markdown
# 一级标题（H1，全文只有一个，等于文件名）

> 状态块

## 一、二、三（H2，用中文数字）
### 1.1（H3，用阿拉伯数字）

正文
```

**不跳级**（H2 下面直接 H4）。层级超过三层，说明这一节该拆成独立文档了。

**末尾放"待定项"或"已知薄弱点"。** 一份没有缺口的文档，通常意味着作者没想透——或者没敢写。

---

## 四、必须写进文档的三类内容

| 类型 | 为什么 |
|---|---|
| **失败的可能** | "如果测出来不成立，就如实写"。写下来是为了到时候不用挣扎 |
| **决策的理由与代价** | 见 [ADR](../02_过程记录/决策记录/) ——"为什么不用 H750"不写下来，半年后会被反复问 |
| **数字的出处** | 每个引用来的数字标 `[n]`，[n] 指向 [文献调研报告](../01_立项/04_文献调研报告.md) |

---

## 五、术语表

统一译法，避免同一件事三种叫法。新术语在首次出现时加一句解释。

| 中文 | 英文 / 缩写 | 一句话解释 |
|---|---|---|
| 端到端时延 | end-to-end latency | 从摄像头出帧到执行器收到指令的总时间 |
| 纯推理时延 | inference latency | 只有模型前向计算的时间 |
| 量化饱和率 | quantization saturation ratio | 激活值被 clamp 到 ±127 的占比（本项目 S2 信号） |
| 三档判定 | W/U/R grading | 可用（Workable）/ 存疑（Uncertain）/ 弃用（Reject） |
| 定向复核 | targeted re-check | 只在存疑时唤醒超声，对准框方位测距 |
| 触发率 | trigger rate | 被判 U 或 R 的帧占总帧数的比例 |
| 覆盖率 | coverage | 1 − 触发率，即"被接受的帧"的占比 |
| 帧间补位 | inter-frame extrapolation | 用惯性信息把旧框推演到当前时刻 |
| 风险—覆盖率曲线 | risk–coverage curve | 横轴覆盖率、纵轴错误率的曲线，用于评价选择性判定 |
| 单视觉基线 | vision-only baseline | 关掉判定与复核的对照配置，一切"下降 X%"都和它比 |

**同一个概念，全仓库只用一种叫法。** 改叫法要做全局替换，不能新旧混用。

---

## 六、文档的维护

- 文档改动同样走 PR（小改可直接推 `main`），说明**改了什么、为什么改**。
- 文档过期比没有文档更糟。**发现一处过期，顺手改掉，别记在待办里**——待办清单会烂，顺手改不会。
- 里程碑验收时，检查那一级相关文档是否与实测一致。**实测数据出来后，估算值必须被替换或明确标注"未更新"**。
- 一学期下来，删掉那些从来没人看、也没人维护的文档。**仓库里躺着的死文档会降低所有文档的可信度。**
