# 指标定义与验收口径

> 状态：v1.0（2026-10-26 定稿）。**改动需组会通过并记入 [变更记录](../06_风险与变更/02_变更记录.md)。**

## 一、四个主指标（对应创新点，能证伪）

### 1. 错误帧召回 @ 触发率 ≤ 30%

| 项 | 定义 |
|---|---|
| 错误帧 | 与真值 IoU < 0.5，**或**类别错，**或**应有框而无框（漏检） |
| 触发 | 该帧被判为 U 或 R |
| 召回 | 被触发的错误帧 / 全部错误帧 |
| 约束 | 触发率 = 触发帧 / 总帧 ≤ 30% |
| 数据来源 | 离线评估集（≥ 300 帧，含正常与困难场景），`tools/eval/` 脚本输出 |
| 目标 | **召回 ≥ 70%** |

**报告方式**：一条风险—覆盖率曲线 + 曲线上的目标点。**只报一个数字不够**，必须给整条曲线，否则看不出"在哪一段掉的"。

### 2. 误动作率

| 项 | 定义 |
|---|---|
| 一次决策 | 底盘每收到一包感知结果，产生一次运动指令，算一次决策 |
| 错误动作 | 视觉给出错误框（同上"错误帧"定义）**且**底盘据此执行了与该错误框一致的动作（朝错误方向转 / 对不存在的障碍减速 / 对存在的障碍未减速） |
| 误动作率 | 错误动作次数 / 总决策次数 |
| 数据来源 | 底盘 100 ms 日志 + 视频回放人工标注（两遍，不一致则第三人裁定） |
| 基线 | **本项目自己的单视觉基线**（关掉判定与复核，同路线同速度跑 20 次） |
| 目标 | 相对基线**下降 ≥ 50%** |

> **"人工标注"是这套指标最弱的一环**，必须写清楚：谁来标、标几遍、分歧怎么处理。不做这一步，"误动作率"就是自我感觉。

### 3. 漏检代价

| 项 | 定义 |
|---|---|
| 漏检事件 | 真值存在但有框缺失，或框 IoU < 0.5 |
| 漏检代价 | 该事件发生时刻，车与障碍的最近距离（cm），分级：> 20 cm / 10–20 cm / 5–10 cm / < 5 cm / 接触 |
| 数据来源 | 超声测距日志（10 Hz 记录最近距离）+ 视频回放 |
| 目标 | **W 档漏检事件的"< 10 cm"占比不高于全帧固定融合基线** |

**为什么用分级而不是平均数**：撞车是极值事件，平均数会掩盖危险的长尾。

### 4. 平均决策时延

| 项 | 定义 |
|---|---|
| 起点 | 摄像头 VSYNC 上升沿（GPIO 打点） |
| 终点 | 底盘 PWM 寄存器写入时刻（GPIO 打点） |
| 平均时延 | 均值（ms） |
| P95 时延 | 95 分位（ms）——**这一项比均值重要** |
| 数据来源 | 逻辑分析仪 / 双通道示波器，测 200 次以上 |
| 目标 | 只记录，不设上限；但**触发率必须 ≤ 30%**，且 U 档时延要单独报 |

**必须分档报**：W 档 ≈ 235 ms、U 档 ≈ 310 ms 是设计值，实测分别填。**混在一起平均会掩盖最坏情况。**

## 二、辅助指标（证明"没退化"，不证明创新）

| 指标 | 定义 | 用途 | 目标 |
|---|---|---|---|
| mAP@0.5 | 标准定义，离线评估集 | 证明模型本身没被量化搞坏 | 相对浮点损失 < 3 个点 |
| 端到端帧率 | 1 / 平均时延 | 证明达到"能演示"的门槛 | ≥ 3 fps |
| 静态 RAM 占用 | 链接后 `.bss + .data + heap + 各任务栈` | 证明内存账算得对 | ≤ 70% 物理 RAM |
| 栈峰值 | 用填充法（`0xDEADBEEF` 填栈，跑满后数未覆盖字节） | 证明不会栈溢出 | 峰值 ≤ 70% 分配栈 |
| Flash 占用 | 链接后 `.text + .rodata` | | ≤ 50% 物理 Flash |
| 功耗—温升—帧率包线 | 满负荷连续 30 min，每 30 s 记电压/电流/板温/帧率 | 证明能连续跑多久 | 给出安全续航（分钟） |

**栈峰值必须实测，不能靠估。** Cube.AI 的推理函数调用层次深，估算经常差一倍——而栈溢出在小车上的表现是"随机死机"，最难查。

## 三、每级验收清单

对着勾，勾不满就是没过。

### M1 · 调研与选型（2026-11-30）

- [ ] 相机出图：连续抓 100 帧不丢帧，能存成文件在 PC 上打开
- [ ] Cube.AI 跑通一个官方模型（最小那个），板端跑起来
- [ ] 实测 RAM / Flash 与 model zoo 账目差异 ≤ 10%，差异有解释
- [ ] 两板串口通信打通，往返延迟有实测值（目标 < 10 ms）
- [ ] 静态内存规划表出第一版（哪个 buffer 放哪块 RAM：DTCM / AXI SRAM / SRAM4）
- [ ] BOM 定稿，采购下单

### M2 · 模型量化与部署预演（2027-02-19）

- [ ] 数据集 ≥ 800 张、≥ 3 类，标注规范成文，抽检一致率 ≥ 95%
- [ ] PC 端 INT8 量化链路跑通（浮点 → INT8 → 推理 → 后处理 → 出框）
- [ ] mAP 相对浮点损失 < 3 个点，损失按类别分解
- [ ] 四个信号 S1–S4 在 PC 端能逐帧算出，生成第一版风险—覆盖率曲线
- [ ] 相关性分析：S1–S4 的相关系数矩阵（**结果可能是"实际只有两个信号有效"，如实记**）

### M3 · 端侧推理跑通（2027-04-14）

- [ ] 模型上板，端到端 ≥ 3 fps
- [ ] 静态内存不溢出，栈峰值实测 < 70%
- [ ] 时序预算表（[系统架构](01_系统架构.md) 第五节）全部填实测值
- [ ] 三档判定在板端实时输出（S2 至少做到 P1 方案：输出层饱和率）
- [ ] **卡点判定**：若 < 2 fps 或内存压不下去 → 触发预案，砍 ③

### M4 · 多传感器融合与整车联调（2027-06-16）

- [ ] 触发式复核接入，实车能演示"存疑 → 降速 → 复核 → 通过/否决"全流程
- [ ] 触发率 ≤ 30%（实车 20 次统计）
- [ ] 单视觉基线数据已采集（关掉判定与复核，20 次）
- [ ] 中期检查可现场演示（**演示脚本提前排练 3 次以上，包含一次故意触发复核**）
- [ ] 三件必证伪的事（[②](04_触发式定向复核.md) 第六节）各有一组数据

### M5 · 系统优化与数据集齐（2027-07-15）

- [ ] 帧间补位上线，A/B 两组各 20 次数据齐
- [ ] 四个主指标全部有数（召回、误动作率、漏检代价、时延含 P95）
- [ ] 功耗—温升包线测完（满负荷 30 min）
- [ ] 部署流程文档写完（别人照着能跑，找一个人实测验证）

### M6 · 结题（2027-08-15）

## 四、口径纪律

1. **指标定义在测之前定死。** 测完再改 = 造假，不论动机多合理。
2. **负结果照写。** "没做通"写"没做通"，不改成"初步验证了可行性"。
3. **基线必须先测。** 没有单视觉基线，"下降 50%"无从谈起——**这是最容易拖到最后就没了的一步，M4 就要求采完。**
4. **原始数据留档。** 每个数字对应一份 `results/raw/` 下的日志或截图，能追到。
5. **别人能复现。** 结题前必须找一个没参与的人照文档跑一遍——**这一条是最硬的验收，也最容易被跳过。**
